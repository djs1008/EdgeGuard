# EdgeGuard 嵌入式 AI 故障诊断项目：开发流程与 Codex 任务手册

> 项目中文名：面向旋转设备的多传感器边缘智能状态监测与故障诊断系统  
> 英文名：**EdgeGuard: A Multi-Sensor Edge AI System for Equipment Condition Monitoring and Fault Diagnosis**  
> 文档用途：项目总体路线图、阶段验收清单，以及可直接交给 Codex 执行的任务提示词  
> 建议仓库路径：`docs/development-guide.md`

## 1. 项目定位

EdgeGuard 是一个围绕小型电机和风扇搭建的完整嵌入式 AI 项目。系统通过振动、电流和温度数据判断设备运行状态，在 STM32 上完成实时采集、信号处理与 TinyML 推理，在 Orange Pi 3B 上完成数据存储、可视化、告警和诊断报告。

项目应形成完整闭环：

```text
故障工况设计
    → 多传感器数据采集
    → 数据清洗、分窗与标注
    → 特征与模型对比
    → 模型量化和 MCU 部署
    → 网关、数据库与仪表盘
    → 系统测试、作品集和演示
```

首要原则不是一次做完全部功能，而是让每个阶段都产生一个可运行、可测试、可提交的版本。

### 1.1 最终演示目标

以正常运行作为基线。人为给风扇叶片增加安全的小配重或改变固定状态后，系统应当：

1. 检测振动特征变化；
2. 输出已知故障类别或未知异常分数；
3. 在 STM32 本地触发 LED/蜂鸣器告警；
4. 将事件上传至 Orange Pi；
5. 在网页显示实时数据、频谱、健康度和历史告警；
6. 保存异常前后数据，生成有依据的诊断建议。

### 1.2 项目范围

必须完成：

- STM32F407 多传感器采集；
- 定时采样、DMA/缓冲区和可靠串口通信；
- 振动信号滤波、分窗、时域/频域特征；
- 自建并版本化管理数据集；
- 至少一个分类模型和一个异常检测基线；
- 至少一个量化模型在 STM32 本地推理；
- Orange Pi 数据接收、数据库、API 和基础仪表盘；
- 告警、故障事件留存和系统测试；
- README、架构、测试和模型性能文档。

可选进阶：

- FreeRTOS、多设备接入、MQTT；
- 异常事件“黑匣子”；
- 模型版本管理和安全更新；
- Docker 部署、CI、自动化硬件在环测试；
- 自定义 PCB 和外壳；
- 麦克风、转速传感器、CAN/RS485。

不在首版范围：

- 一开始就加入声音识别；
- 未建立数据基线前直接训练深度网络；
- 让大语言模型替代传感器算法做故障判定；
- 在没有回滚和完整性校验时实现远程固件升级；
- 同时接上全部模块后再排错。

## 2. 当前硬件基线

| 类别 | 当前方案 | 主要用途 |
|---|---|---|
| MCU | STM32F407VGT6 Type-C 核心板，1 MB Flash | 实时采集、控制、DSP、TinyML |
| 调试 | ST-Link，SWD | 下载、断点、变量和故障定位 |
| Linux 网关 | Orange Pi 3B | 采集服务、数据库、API、网页 |
| 振动 | ADXL345 ×2 | 三轴加速度；首版先使用 1 个 |
| 电流 | INA219 ×2 | 电压、电流与功率监测 |
| 温度 | DS18B20 模块及 1 m 探头 | 电机/风扇温度趋势 |
| 被测设备 | 130 有刷直流电机 ×2、蓝色叶片 | 构造正常、不平衡、负载等状态 |
| 被测设备 | 12 V、8 cm、两线风扇 ×1 | 稳定的旋转设备演示平台 |
| 执行与供电 | MOSFET 模块 ×2、XL4015、12 V 2 A 适配器 | PWM、开关和电机降压供电 |
| 人机交互 | OLED、红黄绿 LED、按键、有源/无源蜂鸣器 | 状态显示与本地告警 |
| 通信 | USB 转 TTL | STM32 与电脑/Orange Pi 串口通信 |
| 原型材料 | 面包板、杜邦线、洞洞板、排针、铜柱、热缩管 | 搭建和固定 |
| 保护与去耦 | 1N5822；0.1/10/100/470 μF；常用电阻 | 续流、滤波、去耦、限流 |
| 功率线 | 22AWG 红黑软线 | 电机、风扇和电源连接 |

### 2.1 电气安全规则

- 首次通电前用万用表确认 12 V 适配器极性和实际输出；
- 130 电机从约 3 V 起测，经 XL4015 调压，不得直接接 12 V；
- STM32、外部电源、传感器和 MOSFET 控制端必须共地；
- 电机与风扇不得由 STM32 板载电源直接供电；
- 电机端增加 0.1 μF 抑制电容；续流二极管方向必须复核；
- 改线必须断电；温升、异味、异常噪声出现时立即断电；
- 堵转测试只允许低电压、短时间、人工看护，并在软件中设置超时和过流阈值；
- 故障模拟以可控、可复现、不损坏器件为前提。

### 2.2 初始采样建议

下面是起点，不是最终参数；应以 ADXL345 实际配置、机械转速、混叠测试和数据结果修正。

| 信号 | 起始配置 | 说明 |
|---|---|---|
| 振动 | 800 Hz 或设备稳定支持的最接近 ODR | 先验证丢样与噪声；不要在文档中虚报 2 kHz |
| 电流 | 100–200 Hz | 注意 INA219 转换时间和总线吞吐 |
| 温度 | 1 Hz | 温度变化慢；避免阻塞式等待转换 |
| 推理窗口 | 1–2 s，50% 重叠 | 后续由模型实验决定 |

## 3. 系统架构

```text
130 电机 / 12 V 风扇
   │
   ├── ADXL345：三轴振动
   ├── INA219：电压/电流/功率
   └── DS18B20：表面温度
             │
             ▼
STM32F407VGT6
   ├── 驱动与定时采样
   ├── 缓冲、质量检查和时间戳
   ├── 滤波、分窗、FFT/特征
   ├── 分类 + 异常检测
   ├── PWM、LED、蜂鸣器、OLED
   └── 带版本和 CRC 的串口协议
             │ UART / USB-TTL
             ▼
Orange Pi 3B
   ├── 数据接收与设备会话
   ├── SQLite（首版）
   ├── FastAPI
   ├── 实时/历史仪表盘
   ├── 告警与事件数据包
   └── 模型和设备版本记录
             │
             ▼
浏览器 / 作品集演示 / 诊断报告
```

### 3.1 软件边界

- **STM32** 是确定性实时层：断网后仍能采集、推理和告警。
- **Orange Pi** 是管理与分析层：保存历史、展示趋势、维护设备和模型信息。
- **训练环境** 负责数据处理、实验复现、模型转换和性能报告。
- **大语言模型** 如后续加入，只能基于结构化指标和规则库解释结果，不能成为唯一故障判据。

### 阶段 1：到货验收、最小系统与开发环境

**目标**

- 核对 STM32F407VGT6 型号和板卡资料；

3. 仅连接 STM32 与 ST-Link；

- 从干净检出可按文档构建；
- 连续运行 30 分钟，无意外复位；
- 串口输出包含固件版本、复位原因和递增序号；
- 能使用 ST-Link 断点调试。

### 阶段 2：传感器逐个驱动与校验

**目标**

- 按 ADXL345 → INA219 → DS18B20 的顺序逐个接入；
- 每次只增加一个模块；
- 将总线、驱动、应用层分开。

**验收**

- ADXL345 能读取器件 ID、量程/ODR 配置和三轴原始值；
- 静止时模长接近 1 g，方向变化合理；
- INA219 与万用表在定义好的负载点对比并记录误差；
- DS18B20 完成 ROM/CRC、非阻塞温度转换和异常值处理；
- 传感器断开或总线错误不会让主循环永久卡死。

**给 Codex 的任务 2A：ADXL345 驱动**

```text

要求：
- 总线访问通过可替换接口注入，驱动层不直接依赖应用逻辑；
- 初始化后读回关键寄存器校验；
- 提供原始值和 SI 单位转换；
- 对超时、错误 ID、总线失败返回明确错误；
- 添加主机侧可运行的寄存器解析/换算测试；
- 更新 docs/sensors/adxl345.md，包含接线、配置、坐标、校准和实机测试步骤。
```

### 阶段 3：统一采集、缓冲和通信协议

**目标**

- 以硬件定时器形成稳定时间基准；
- 建立多速率采样、缓冲区和数据质量计数；
- 定义同一份协议规范并实现 C 编码端和 Python 解析端。

**建议协议字段**

```text
magic | version | device_id | message_type | flags |
sequence | timestamp_us | payload_length | payload | crc16
```

帧格式应定义字节序、最大载荷、转义/分帧策略、错误码、兼容规则和 CRC 参数。原始振动流与低频遥测应使用不同消息类型。

**验收**

- 连续运行至少 2 小时；
- 序号可测量丢帧、重复帧和乱序；
- Python 解析器能从噪声和截断输入中重新同步；
- 记录采样抖动、缓冲高水位、传感器错误和 UART 丢包；
- 协议的 C/Python 黄金向量一致。

**给 Codex 的任务 3A：协议设计与双端实现**

```text
为 EdgeGuard 设计版本化二进制串口协议，并写入 docs/protocol.md。协议必须包含 magic、版本、设备 ID、消息类型、flags、序号、设备时间戳、载荷长度、载荷和 CRC16；明确字节序、最大帧长、CRC 变体、错误恢复和向后兼容策略。

实现：
- STM32 C 端无动态内存编码器；
- Python 流式解析器，可处理粘包、拆包、噪声、坏 CRC 和重新同步；
```

### 阶段 4：数据集设计、采集与质量控制

**目标**

- 采集多个会话、速度、安装方式和日期；

**建议标签（按可安全复现程度逐步加入）**

- `normal_low`、`normal_medium`、`normal_high`
- `unbalanced`
- `loose_mount`
- `overload`
- `blocked_short`（低压、短时、看护）
- `unknown_anomaly`

**数据划分原则**

- 预处理参数只在训练集拟合；

- 每类至少包含多个独立会话，而非一条长记录；

## 8. Git 与质量规则

### 8.1 分支与提交

- `main`：始终保持可展示；
- 功能分支：`feature/adxl345-driver`、`feature/serial-protocol`；
- 修复分支：`fix/uart-resync`；

```text
feat(firmware): add ADXL345 identity and config checks

```

一次提交只表达一个完整意图。不要提交密钥、个人路径、大型原始数据、自动生成编译目录和未经确认的二进制模型。

### 8.2 Definition of Done

一项任务只有同时满足以下条件才算完成：

- 需求和接口明确；
- 代码可构建或脚本可运行；
- 自动测试通过；
- 必要的实机测试有记录；
- 错误路径和边界条件已考虑；
- 文档、协议、模型/固件版本已同步；
- 无无关改动和敏感信息；
- 未验证项被明确标注，而不是隐藏。

- 训练脚本、指标报告、模型转换和部署辅助；
- 后端、数据库、前端和部署配置。

必须由项目作者确认并能解释：

- 原理图、引脚、电压、极性和器件真实参数；
- 采样率、混叠、滤波、窗口和 FFT 选择；
- 工况构造是否安全、标签是否可信；
- 数据划分和模型选择；
- 中断、DMA、缓冲所有权、RTOS 优先级；
- RAM/Flash/栈预算和推理延迟；
- 保护电路与故障恢复；
- 简历中每一个技术数字。

## 9. 建议的首周执行清单

硬件尚未到齐时：

1. 执行任务 0A，建立仓库和文档；
2. 安装并记录 STM32CubeMX、STM32CubeIDE、ST-Link 工具和 Python 版本；
3. 收集核心板原理图、ADXL345/INA219 模块照片和丝印；
4. 建立 `hardware/bom/bom.md`，逐项标记“已购买/已到货/已验收”；
5. 冻结 V0.1 的验收标准。

硬件到货后：

1. 拍照并核对型号、焊接和损伤；
2. 万用表检查供电与降压输出；
3. 只接 F407 + ST-Link，完成点灯和串口；
4. 单独验证 ADXL345；
5. 单独验证 INA219；
6. 单独验证 DS18B20；
7. 低压测试 130 电机，再测试 MOSFET/PWM；
8. 所有模块分别通过后才进入统一采集。

## 10. V1.0 完成判定

EdgeGuard V1.0 不以“代码很多”为完成标准，而以以下证据为准：

- 一个能独立运行和本地告警的 STM32 节点；
- 一个可复现、无明显数据泄漏的多会话数据集；
- 一个在留出会话上有诚实指标的分类模型；
- 一个有阈值依据和误报统计的异常检测方案；
- 一个在 STM32 上实测过 RAM、Flash 和延迟的量化模型；
- 一个可断线恢复、保存历史和展示告警的 Orange Pi 网关；
- 一套带测试记录的协议、故障注入和长时间运行结果；
- 一份任何面试官都能按步骤理解和复现的文档；
- 一段演示系统价值、而不是只展示界面的短视频；
- 一条只陈述真实完成内容的简历项目经历。

达到这些条件后，再进入 PCB、外壳、OTA、声音传感、多设备和云端扩展。这样 EdgeGuard 才会成为一个真正完整、可讲清楚、可持续迭代的嵌入式 AI 作品，而不是功能清单。
